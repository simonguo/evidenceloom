## Observed problem and resulting behavior

The previous frontend removed a task and announced success before its native deletion acknowledgement; the actual detail page also navigated immediately. The native clear-data command did not consult retained analysis ownership. A remounted UI could therefore consider itself idle while the native runtime still owned work. Existing retained recovery experiments confirm the missing reconciliation with actual helpers and React components under controlled transport; they do not exercise real WebView IPC or a user database.

The native registry now rejects clear-data callbacks while any unexpired reservation, preparing/running owner or incomplete cleanup remains. It holds the active-owner mutex across the entire synchronous clear callback, serializing it with admission and release. The command dispatches that operation to a blocking worker. Reservation also uses a production async blocking-worker helper so waiting for this mutex yields. [Tauri documents](https://v2.tauri.app/develop/calling-rust/#async-commands) synchronous command execution on the main thread and asynchronous command execution as a separate task; local macro sources for Tauri 2.11.5 and tauri-macros 2.6.3 were checked. This does not establish a total filesystem deadline or a hard bound on every control path.

Desktop task deletion keeps the currently displayed task until the native adapter acknowledges success, coalesces concurrent requests for the same task and returns a boolean result. Rejection preserves the current UI and displays a localized unknown-outcome/retry notice. The actual detail-page caller closes its menu and navigates only after a true result. A selection identity, unmount guard and pending-attempt guard prevent old acknowledgements from changing a different selected page or navigating twice. Browser deletion retains its immediate local behavior.

UI retention does not prove disk retention. The unchanged native storage implementation commits `DELETE FROM tasks` before evidence pruning; pruning failure or acknowledgement loss can follow a successful deletion. The final message therefore says deletion could not be confirmed and the task temporarily remains in the list. No transactional deletion rollback is claimed.

## Remaining acceptance

This slice does not implement authoritative refresh/remount recovery. The pending deletion map is memory only, and a never-settling acknowledgement has no deletion deadline. Queued/direct saves can still reinsert after delete or clear; no task revision, tombstone, collection epoch, CAS, storage transaction or queue-dispatch barrier is added. The clear callback has no total I/O deadline or atomic rollback, and other controls or cleanup release can still wait for that global mutex. Passing reservation-yield evidence does not establish a universal cleanup bound.

Retained exact-base recovery experiments still report five failed desired React recovery assertions. Fresh frontend realms cannot query/reconnect an existing owner; per-registry run nonces can repeat after runtime replacement, which matters for any future persisted control token. Runtime epoch, immutable run context, ordered event replay, a native durable terminal journal, same-database projection/cursor transactions, cleanup-plus-durability dispatch gates and stale-write protection remain required.
